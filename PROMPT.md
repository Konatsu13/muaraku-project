# MUARAKU — MASTER IMPLEMENTATION PROMPT

You are the lead full-stack engineer, software architect, UI/UX engineer, and security reviewer responsible for completing MuaraKu, an AI-powered lost-and-found platform for Indonesia.

## 1. Read Before Acting

Before changing any code, inspect the existing repository and read these documents if available:

- `PRD.md` — product requirements and implementation roadmap.
- `DESIGN.md` — design system, page specifications, interactions, and UI requirements.
- `muaraku_supabase_schema.sql` — proposed database schema and security policies.
- `README.md`, `package.json`, environment examples, existing migrations, and relevant source files.

Treat the actual repository and deployed configuration as the source of truth for what currently exists. Documentation describes intended behavior, not proof that a feature has already been implemented.

Do not assume that all files, database tables, integrations, or UI components are complete.

## 2. Audit First

Before implementation:

1. Identify the framework, router, language, package manager, folder structure, and current application architecture.
2. Identify completed features, incomplete features, prototypes, mock data, duplicated components, and broken flows.
3. Review Supabase Auth, database schema, RLS policies, Storage policies, Realtime subscriptions, and existing migrations.
4. Inspect the current Stitch-generated designs and compare them with `DESIGN.md`.
5. Identify security, accessibility, responsive-layout, and production-readiness gaps.
6. Produce a concise prioritized audit report.

Do not stop after the audit. After presenting the findings, continue with the highest-priority safe implementation steps unless a destructive action or genuinely blocking decision requires approval.

## 3. Product and Design Principles

- Preserve MuaraKu's brand identity, logo meaning, color system, and established design language.
- Use `DESIGN.md` as the design baseline, not an excuse to reproduce weak or incomplete designs.
- You may improve layouts, typography, spacing, navigation, responsiveness, empty states, loading states, error states, and interactions when doing so improves usability.
- Create missing screens and components that are required by `PRD.md`.
- Keep improvements consistent across the application.
- Do not replace working features merely to make the code look cleaner.
- Do not leave placeholder buttons, fake functionality, or hardcoded mock data in production flows.
- Maintain accessible labels, keyboard navigation, readable contrast, and responsive behavior.

## 4. Core Product Requirements

Prioritize a complete lost-and-found workflow:

1. Authentication and account management.
2. Seeker and Finder reports.
3. Discover feed, search, filters, and report details.
4. Private claims and evidence submission.
5. Private messaging and report status updates.
6. Notifications and basic moderation.
7. Admin controls and audit logs.
8. Muara Search AI and Muara CS AI.
9. Global Chat and its scheduled daily reset, if included in the active MVP scope.
10. Indonesian and English localization across all supported UI.

Follow the priority order in `PRD.md`. If time or complexity becomes a problem, finish the critical workflow before starting optional features.

## 5. Security Requirements

- Enforce authorization on the server and in database policies, not only in the UI.
- Verify Supabase RLS and Storage policies against unauthorized access.
- Never expose Supabase secret/service-role keys, OpenAI API keys, Resend API keys, or other secrets to client-side code.
- Do not trust client-supplied user IDs, role names, ownership claims, or admin flags.
- Private conversations and claim evidence must only be accessible to authorized users.
- Do not treat AI-generated matches as proof of ownership.
- Validate all AI output before using it in application logic.
- Apply rate limits and appropriate error handling to sensitive endpoints.
- Never execute arbitrary SQL generated by an AI model.
- Do not claim end-to-end encryption unless it is actually implemented and verified.
- Do not run destructive migrations, delete production data, or disable security policies as a shortcut.

## 6. AI Architecture

Use the existing architecture if it is already sound. The intended architecture is:

- Next.js and TypeScript for the web application.
- Supabase for authentication, PostgreSQL, storage, and realtime features.
- Python FastAPI as a separate AI service when required by the project.
- OpenAI API for Muara Search AI and Muara CS AI.

Keep Search and CS logically separated through distinct instructions, validated inputs/outputs, access rules, logging, and usage limits.

Do not create unnecessary databases or additional AI agents without a concrete requirement.

## 7. Internationalization

Support Indonesian (`id`) and English (`en`).

Before implementation:

- Detect whether the project uses Next.js App Router or Pages Router.
- Inspect existing localization code and dependencies.
- Select a compatible i18n approach rather than installing duplicate libraries.
- Implement a persistent language selector in Settings and any other location specified in `DESIGN.md`.
- Translate navigation, pages, forms, validation messages, notifications, dialogs, accessibility labels, loading states, and error states.
- Preserve user-entered report descriptions and chat messages; do not silently translate or rewrite user content.
- Store user language preference persistently when authenticated and provide a sensible default for guests.
- Avoid hardcoded interface strings and avoid mixing languages on the same screen.
- Handle dates, numbers, and relative times using the selected locale.
- Ensure locale changes do not break routes, authentication callbacks, or existing deep links.

## 8. Engineering Workflow

For each implementation phase:

1. State the goal and relevant files.
2. Make small, focused changes.
3. Preserve existing project conventions.
4. Add or update tests.
5. Run the available lint, type-check, test, and production-build commands.
6. Fix regressions introduced by your changes.
7. Report any test that could not be run and why.
8. Update `TASKS.md` and `CHANGELOG.md` if they exist.
9. Document any environment-variable or migration requirements.

Do not claim a feature works unless you have verified it through code inspection or testing.

Do not fabricate test results. Do not silently swallow errors. Do not rewrite the whole repository in a single operation.

## 9. Completion Report

At the end of each phase, report:

- What was implemented.
- Which files changed.
- Dependencies added or removed.
- Database migrations required.
- Environment variables required, using placeholders only.
- Tests and build commands executed, with actual results.
- Known limitations and unresolved security risks.
- The recommended next step.

Begin by auditing the repository and comparing it with `PRD.md` and `DESIGN.md`. Then proceed in prioritized, testable phases. Your goal is a reliable, secure, polished MVP that can be demonstrated and deployed—not simply a large quantity of generated code.

## WAJIB: CHANGELOG, TASK TRACKING & AI HANDOFF

Tujuan: memastikan proyek dapat dilanjutkan oleh AI Agent lain kapan pun agent saat ini terkena usage limit, mengalami kegagalan, sesi terputus, atau pekerjaan dialihkan.

### 1. File dokumentasi yang wajib dipelihara

Buat atau perbarui file berikut di root repository:

- `CHANGELOG.md` — riwayat perubahan yang benar-benar sudah dilakukan.
- `TASKS.md` — status pekerjaan seluruh fitur dan subfitur.
- `HANDOFF.md` — kondisi terakhir proyek dan instruksi konkret untuk agent berikutnya.

Sebelum membuat file baru, periksa apakah file tersebut sudah tersedia. Pertahankan informasi historis yang masih relevan dan hindari duplikasi.

### 2. Aturan pencatatan

Setiap kali menyelesaikan satu unit pekerjaan yang bermakna:

1. Perbarui `CHANGELOG.md` dengan perubahan, alasan, dan dampaknya.
2. Perbarui `TASKS.md` dengan status pekerjaan terbaru.
3. Perbarui `HANDOFF.md` agar agent berikutnya bisa melanjutkan pekerjaan tanpa harus menebak kondisi repository.

Jangan hanya memperbarui dokumentasi di akhir sesi. Lakukan pembaruan secara berkala, terutama setelah menyelesaikan satu fitur, migrasi database, perubahan autentikasi, integrasi AI, atau perubahan arsitektur.

Catat hanya fakta yang bisa diverifikasi. Bedakan dengan jelas antara:
- Selesai dan sudah diuji.
- Selesai tetapi belum diuji.
- Sedang dikerjakan.
- Belum dikerjakan.
- Terblokir atau membutuhkan keputusan.
- Gagal atau perlu diperbaiki.

Jangan pernah menyatakan fitur berfungsi hanya karena kodenya telah ditulis.

### 3. Format CHANGELOG.md

Gunakan tanggal dan kategori perubahan, misalnya `Added`, `Changed`, `Fixed`, `Security`, `Database`, `AI`, dan `Internationalization`.

Setiap entri harus menjelaskan:
- Apa yang berubah.
- File atau komponen yang terdampak.
- Alasan atau tujuan perubahan.
- Status pengujian.
- Catatan migrasi, konfigurasi, atau risiko jika relevan.

Jangan menimpa riwayat lama. Tambahkan entri baru secara kronologis dengan format yang konsisten.

### 4. Format TASKS.md

Kelompokkan tugas berdasarkan fitur atau fase implementasi. Gunakan status yang konsisten:

- `[x]` Selesai dan terverifikasi.
- `[~]` Sedang dikerjakan atau baru selesai sebagian.
- `[ ]` Belum dikerjakan.
- `[!]` Terblokir atau memerlukan perhatian.

Setiap tugas yang belum selesai harus memiliki informasi yang cukup untuk ditindaklanjuti:
- Hasil yang sudah dicapai.
- Bagian yang masih tersisa.
- Dependensi atau prasyarat.
- Kendala dan alasan penundaan.
- Prioritas berikutnya.

Jangan mengubah tugas menjadi selesai hanya karena implementasi parsial telah dibuat.

### 5. Format HANDOFF.md — paling penting

File ini adalah sumber utama bagi agent berikutnya untuk melanjutkan pekerjaan.

Selalu sertakan bagian berikut:

**A. Project Context**
- Tujuan proyek dan arsitektur yang terverifikasi.
- Framework, bahasa, package manager, dan layanan yang benar-benar digunakan.
- Referensi dokument
